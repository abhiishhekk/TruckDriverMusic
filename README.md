# Truck Driver Anthems

A static React + Vite site: a dusk highway/dhaba scene, a hero title
framed like the hand-painted back of an Indian truck, and a working
playlist player driven by the YouTube IFrame Player — not the YouTube
Data API — so playback has no per-visitor quota.

## Tech stack

- **React 18** (function components + hooks only)
- **Vite** — dev server and build tool
- Plain CSS per component (no Tailwind/MUI)
- **YouTube IFrame Player API** for actual playback (loaded lazily by
  `src/hooks/useYouTubeIframeApi.js`)
- A one-off **Node script** (`scripts/fetch-playlist.mjs`) that talks
  to the YouTube Data API — but only when *you* run it locally, never
  from a visitor's browser

## Why there's no visitor-facing API limit

YouTube's Data API (the thing with the 10,000-units/day quota) is for
*metadata* — titles, channel names, playlist contents. It is **not**
what streams the video. The IFrame Player embed that actually plays a
video runs on separate, unmetered infrastructure — the same thing
that lets any website embed a YouTube video without a quota.

So the design here is:

1. `scripts/fetch-playlist.mjs` calls the Data API **once, on your
   machine**, to pull every video ID + title out of your two source
   playlists, dedupes them, and writes the result into
   `src/data/playlist.js` as a plain JS array.
2. The deployed site imports that file directly. No `fetch()` to
   YouTube's Data API happens at runtime, for any visitor, ever.
3. `MusicPlayer.jsx` hands each `youtubeId` to a YT.Player embed for
   actual playback — that part has no daily cap.

Net result: unlimited visitors, no live API calls, nothing to rate-limit.

## Refreshing the tracklist from your playlists

The repo ships with 4 verified seed tracks so it works immediately.
To pull the full, deduplicated contents of your own playlists:

1. Get a free YouTube Data API v3 key: [Google Cloud Console → Credentials](https://console.cloud.google.com/apis/credentials)
   (enable "YouTube Data API v3" on the project first).
2. Copy `.env.example` to `.env` and paste your key in:
   ```bash
   cp .env.example .env
   # then edit .env — it should end up looking like:
   # YOUTUBE_API_KEY=AIzaSy...
   ```
   `.env` is gitignored, so your key never gets committed. If you'd
   rather not use a file at all, you can still do
   `YOUTUBE_API_KEY=your_key npm run fetch:playlist` and skip .env entirely.
3. Run:
   ```bash
   npm run fetch:playlist
   ```
   This overwrites `src/data/playlist.js` with every track from both
   playlists, deduplicated by video ID (a song in both playlists, or
   listed twice in one, only appears once — order is preserved by
   first occurrence). Deleted/private videos are skipped automatically.
4. Commit the regenerated `playlist.js`. From here on, deploying the
   site makes zero further API calls — you'd only re-run this script
   if you want to refresh the list again later.

The two source playlists are hardcoded at the top of
`scripts/fetch-playlist.mjs` (`PLAYLIST_IDS`) — edit that array if you
want to point it at different playlists.

## How the pieces connect

`Home.jsx` is the only place that holds state (`trackIndex`, i.e.
"which song is selected"). It passes that down as props to both
`TrackList` and `MusicPlayer`, so clicking a row in the list and
clicking next/prev in the player control the same thing — the
standard React pattern of **lifting state up** to the nearest shared
parent.

`MusicPlayer` creates one `YT.Player` instance (via
`useYouTubeIframeApi`) and reuses it across tracks with
`loadVideoById()`, rather than creating/destroying a player per song.
Since the IFrame API doesn't emit a continuous "time update" event
the way `<audio>` does, the player polls `getCurrentTime()` every
400ms while something is actually playing, and stops polling the
instant it's paused — so it's not running a timer in the background
for no reason.

## Design notes: the truck-art frame

`TruckArtBorder` is a deliberate homage to the reference photo of a
decorated Indian truck — the diagonal red/yellow "candy stripe" edges
echo the painted chassis stripes, the four corner medallions are a
simplified version of the hand-painted flower motifs, and the two
swaying tassels reference the ones hung from a real truck's mirrors
and grille. All of it is original SVG/CSS in this project, not traced
or copied from the photo — same visual *language*, not the same artwork.

## Live "travellers on the road" count

The `StatusBar` shows a real count of how many browser tabs currently
have the site open — powered by **Firebase Realtime Database**, which
is a free client-only backend (no server code of yours involved).

**One-time setup:**

1. Go to [console.firebase.google.com](https://console.firebase.google.com/)
   → *Add project* (the free **Spark** plan is enough for this).
2. In the left sidebar: **Build → Realtime Database → Create Database**.
   Choose any region, start in **test mode** for now.
3. Go to the Rules tab of that database and replace the default rules
   with something that only allows what this feature needs — clients
   can write *only* their own presence key, and can't write anywhere
   else or read other data:
   ```json
   {
     "rules": {
       "presence": {
         ".read": true,
         "$uid": {
           ".write": true
         }
       }
     }
   }
   ```
4. Back in **Project settings** (gear icon, top left) → scroll to
   *Your apps* → click the **Web** (`</>`) icon → register an app
   (no Hosting needed) → copy the `firebaseConfig` values shown.
5. Paste those values into `.env` (see `.env.example` for the exact
   variable names) and run `npm install` to pull in the `firebase`
   package.
6. `npm run dev` — open the site in two browser tabs and watch the
   count go from 1 to 2.

**How it works:** `src/hooks/useOnlineCount.js` writes a small
"I'm here" entry under `/presence/<random-id>` when a tab connects,
and tells Firebase to delete that entry the instant the socket drops
(tab closed, phone locked, wifi died — no heartbeat polling needed).
Every tab listens to the size of `/presence` and that's the count you
see. Nothing here needs a server you write or host — Firebase's
websocket connection to the client *is* the whole mechanism.

This is entirely optional — if you never fill in the `VITE_FIREBASE_*`
vars, `initializeApp` will just fail quietly-ish and the count will
sit at 1. Delete `useOnlineCount()` from `StatusBar.jsx` if you'd
rather not use it at all.

## Making it yours

- **Change the songs:** re-run `npm run fetch:playlist`, or hand-edit
  `src/data/playlist.js` directly.
- **Change the colors:** edit the `:root` variables at the top of
  `src/index.css` — every component reads colors from there.
- **Change the title:** edit `src/components/HighwaySign/HighwaySign.jsx`.
